# Architecture (deep reference)

On-demand companion to `AGENTS.md`. Read this when you need the full module map; the `AGENTS.md` summary + on-pattern recipes cover most day-to-day work.

**DXKB V2** is a Next.js 16 app (App Router) serving as a Disease X Knowledge Base — a bioinformatics platform for genomics, metagenomics, and viral research.

## App Router structure (`src/app/`)

Route groups `(…)` are organizational and do NOT appear in the URL.

- `/` — Public home page (search, news, statistics)
- `(auth)/` — `sign-in`, `sign-up`, `forgot-password`
- `(footer)/` — static content pages (about, faq, news, privacy-policy, team, etc.)
- `(views)/` — BV-BRC data view pages: `genome`, `taxonomy`, `strain`, `feature`, `epitope`, `experiment`, `serology`, `surveillance`, `protein-structure`, `domains-and-motifs`. The registry supplies route metadata; production views use explicit per-route composition (see **Views & organism landing**)
- `/organisms/(all|bacteria|viruses)/...` — organism landing pages (tabbed; driven by `_config.ts` + view registry)
- `/workspace/...` — workspace file browser. Route shapes: `/workspace/[username]/home/[[...path]]`, `/workspace/[username]/[folder]/[[...path]]`, `/workspace/home/[[...path]]`, `/workspace/shared/[[...path]]`, `/workspace/public/[username]/[...path]`, `/workspace/workshop`
- `/services/(genomics|metagenomics|phylogenomics|protein-tools|utilities|viral-tools)/...` — service submission forms (route groups as categories)
- `/search/` — Global search
- `/jobs/` — Job monitoring
- `/settings/` — user settings
- `/viewer/structure/` — standalone workspace-backed 3D protein structure viewer
- `/api/auth/...` — Custom auth API routes
- `/api/services/...` — Proxied service API routes
- `/api/workspace/...` — Proxied workspace API routes
- `/api/data/[resource]` — validated, rate-limited same-origin gateway to allowlisted BV-BRC Data API resources
- `/api/structure/[...path]` — validated same-origin proxy for BV-BRC-hosted structure files
- `/api/taxon-view/tab-policy` — tab-visibility policy for views (see `docs/taxon-view-tab-visibility.md`)
- `/api/e2e-mock/[...path]` — loopback backend mock used only by the Playwright suite. Its populated fixtures come from `src/lib/e2e-fixtures/records.ts` (dependency-free typed canonical records) + `envelopes.ts` (transport-specific Solr/gateway wrapping), the single source of truth shared with the browser-side mock in `e2e/fixtures/overrides/catchall.ts` — see `e2e/README.md` for the fixture-composition breakdown (empty fallback vs. named resource scenario bundles vs. the a11y-only aggregate)

## Auth system (`src/lib/auth/`) — server-first identity

- `client.ts` — concrete browser functions for retained `/api/auth/*` mutations and profile operations
- `provider.tsx` — `<AuthBoundary user={user}>`, `useAuth()` derived identity, `useAuthActions()` mutations, and the minimal client route guard
- `routes.ts` — protected page classification used by the proxy and client guard
- `types.ts` — browser-safe `AuthUser`, upstream `UserProfile`, credentials, sessions, and `Result` types
- `server/actions.ts` — named auth operations such as `signIn`, `signOut`, `startImpersonation`, and cached `getCurrentUser`
- `server/session.ts` — sole owner of HttpOnly session and SU backup cookie reads/writes
- `server/cookies.ts` — Edge-safe cookie names and optimistic cookie-presence check
- `server/route.ts` — authenticated route wrapping and direct session reads for routes and Server Components
- `server/adapters/bvbrc-identity.ts` — named BV-BRC identity protocol calls

Notes:

- This is custom BV-BRC authentication, not Better Auth. Server rendering validates cookies through `getCurrentUser()` and passes the browser-safe user into `<AuthBoundary>`; the browser does not fetch a session on mount and never receives the BV-BRC token.
- `src/proxy.ts` delegates page classification to `isProtectedPagePath()`. It optimistically checks cookie presence; Server Components and protected API handlers perform authoritative validation.
- The active session cookies are `bvbrc_token`, `bvbrc_user_id`, and optional `bvbrc_realm`, all HttpOnly, SameSite Strict, path `/`, and Secure in production. Explicit sign-out is a redirecting Server Action, not an `/api/auth/sign-out` route.
- `/api/auth/*` wire contracts are documented in `docs/auth-api.md`. Every auth failure uses `{error, code}`.

## Backend communication

- `JsonRpcClient` (`src/lib/jsonrpc-client.ts`) — all backend calls use JSON-RPC 2.0 over HTTP POST; requires `APP_SERVICE_URL` env var
- `AppService` (`src/lib/app-service.ts`) — job management: enumerate/query/kill jobs, submit services via `AppService.start_app2`
- `WorkspaceApiClient` (`src/lib/services/workspace/client.ts`) — workspace CRUD operations
- `src/lib/data-api/` — typed Data API resource registry, validation, RQL serialization, server/browser repositories, normalized response types, and TanStack Query option/key factories. Browser view code uses `/api/data/[resource]`; upstream URLs and BV-BRC tokens remain server-only.
- `src/lib/data-api/server-repository.ts` — `createServerDataRepository()` guards itself with `import "server-only"` and is the single factory every `src/lib/*-view/server.ts` entity-lookup module (`genome`, `feature`, `epitope`, `surveillance`, `serology`, `experiment`, `protein-structure`) uses to build its `ServerDataRepository`. It owns session lookup, `DATA_API_URL`/`NEXT_PUBLIC_DATA_API` resolution, and cache policy only — anonymous requests get `force-cache` with a 300-second revalidation window, authenticated or E2E-mock requests get `no-store` — and throws `new DataApiError("DATA_API_URL is not configured.", 500, "not_configured")` when neither env var is set. That throw is deliberately typed and carries a `code`: callers discriminate this one failure from any other (a `readSession()`/`cookies()` failure, say) with `error instanceof DataApiError && error.code === "not_configured"` instead of catching indiscriminately, and it is the same status/code the gateway route uses for the identical condition. Entity lookup, alternate IDs, compound resolution, parsing, and error semantics stay in each calling module; the factory itself is never wrapped in React `cache()`. The six scalar-ID modules let the missing-config error propagate (each keeps its own `cache()` wrapper around its own exported lookup) so Next redacts the message in production. `protein-structure-view/server.ts` differs on purpose: it resolves an array of accessions, so it is not wrapped in `cache()` at all, and it catches the factory's error — narrowing on exactly `error instanceof DataApiError && error.code === "not_configured"` and rethrowing anything else — to map it onto its existing per-accession `error` field with a generic message plus a `console.error` carrying the env var detail, instead of rendering the variable name into the response.

### Data API gateway contract

- Supported resources: `taxonomy`, `genome`, `genome_feature`, `epitope`, `epitope_assay`, `surveillance`, `serology`, `strain`, `protein_feature`, `protein_structure`, `experiment`, `bioset`, `genome_sequence`, `sequence_feature`, and `ppi`.
- Stable IDs, in the same order: `taxon_id`, `genome_id`, `feature_id`, `epitope_id`, `assay_id`, `id`, `id`, `id`, `id`, `pdb_id`, `exp_id`, `bioset_id`, `sequence_id`, `id`, and `id`. Taxonomy IDs remain positive integer strings at route and selection boundaries. `genome_feature` also accepts `patric_id`; Surveillance and Serology allow their documented compound public identifiers. Identifiers remain strings even when digit-only.
- Resource metadata allowlists field type, selection, sorting, faceting, and RQL quoting. Requests are bounded and validated by resource, operation, identifier, field, operator, range/export size, URL/body size, and rate limit. Sorts gain the stable ID as a deterministic tie-break.
- Upstream item ranges use an exclusive end: `items=0-200` yields 200 rows. Collection pages are one-based and fixed at 200 rows.
- Anonymous public member lookups use five-minute shared caching (`s-maxage=300`). Authenticated/private requests, collections, selected-row requests, and exports use `no-store`.

## Views & organism landing

`src/lib/views/`, `src/components/views/`, `src/hooks/views/`, `src/components/organisms/`, `src/app/(views)`, `src/app/organisms/`

- `src/lib/views/view-registry.ts` — enumerable, data-only route metadata for canonical segments, legacy redirects, search mapping, identifiers, resources, and defaults. Do not put components, fetch functions, columns, or tab query builders in it.
- `src/lib/views/collection-state.ts` — canonical URL-owned collection state. Pages are one-based, sort uses `field:asc|desc`, page 1/default sort are omitted, and filtering changes reset page 1. Page size (200), row selection, and column layout remain outside the URL. `collectionManagedParamNames`/`unionCollectionManagedParamNames` are the one definition of which query params a view (or several views at once) owns and may clear; filter→RQL composition is not here at all — `structural-rql.ts` is the only composer, and the options type carries no field map; `replaceCollectionSearchParams` (full-state replacement, no pagination reset — `useCollectionUrlState`'s `setState` just delegates to it) stays a separate function from `updateCollectionSearchParams` (incremental, resets page on a query-shape change) so the two policies can't get folded together again. `LandingShellClient` (`src/components/organisms/landing-shell/`) unions every organism-tab view's options via `unionCollectionManagedParamNames` to clear cross-tab state on a tab switch, since it can't otherwise know which tab a stray parameter belongs to.
- `src/lib/views/structural-rql.ts` — `structuralFilterRql(resource, state, options?)` is the one shared composer behind every `*StructuralRql` domain wrapper (Genome, Strain, Protein Feature, Epitope, Surveillance, Serology, Experiment/Bioset, Taxonomy, Protein Structure): explicit `state.rql` bypasses friendly filters, values within a field are ORed, fields are ANDed, and it serializes through the Data API `eq`. `options.fieldMap` remaps a friendly filter name to its backend field, and the one remap five of those wrappers need — `taxon_id` → `taxon_lineage_ids` — is the module's own exported `taxonLineageFieldMap`, passed as `fieldMap` by Epitope, Experiment, Protein Structure and Strain and spread into Genome's table (Taxonomy deliberately does not: `taxon_id` already is its own id field, which is why the map is opt-in rather than `fieldMap`'s default); `options.unknownFilters` picks what happens to a name absent from that map — `"passthrough"` (default, used by every wrapper above except Genome) forwards it unchanged, `"drop"` (Genome only) omits it instead, because Genome's remap table is total and authoritative rather than a set of overrides on top of pass-through. Each domain module still owns its typed wrapper function; the helper owns composition and the shared lineage remap. Genome's remap table is the one that is not just the shared map: it is *total* (`unknownFilters: "drop"`), so it is derived from `genomeCollectionOptions.friendlyFilters` rather than restating those names, and the two lists cannot drift apart. Feature (`src/lib/feature-view/query.ts`) is deliberately excluded: its synthetic protein filter accumulates outside the `state.rql` guard, so it applies even when explicit RQL is present, unlike every module above.
- `src/lib/views/field-metadata.ts` — `deriveFieldMetadata(fieldMap, policy)` is the one pass that turns a `src/constants/datafields/*` `DataField` map into a view's `{ columns, detailFields, facets, facetFields, sorts }`. Each entity calls it exactly once, from a `src/lib/*-view/fields.ts` module that both its `profile.ts` (columns/details/facets) and its `query.ts` (sort allowlist/friendly filters) import. A dedicated module for cohesion — the one metadata pass has one obvious home and neither consumer owns it. The alternative worth naming is the *unsafe* one: putting the pass in `profile.ts` and importing it from `query.ts` closes a cycle, because `profile.ts` already imports `query.ts` for `*StructuralRql`, and `query.ts`'s consumer is a module-level `const` (`export const featureSorts = featureMetadata.sorts`) while `*StructuralRql` is a hoisted declaration — so evaluating `profile.ts` first leaves `featureMetadata` in TDZ and throws. Putting the pass in `query.ts` instead would be safe (no `query.ts` imports `profile.ts`, so that direction closes no loop); `fields.ts` is preferred over it on cohesion, not safety. `child-resources.ts` runs the same pass for the three child-tab column sets whose resources have no `*-view/` directory (`genome_sequence`, `ppi`, `sequence_feature`) and consumes `columns` only, since child tabs hold their sort in component state rather than the URL. `genome_feature` is deliberately absent: `ResourceChildCollection` substitutes the Feature collection profile for its feature tabs, so a set declared there would be dead code, and it would also disagree on policy with that profile's columns even if declared — Feature passes `hiddenColumns: "omit"` while `child-resources.ts`'s derivations all use the default collapse policy.
  - **The one contract for the four overlapping visibility flags**, stated in the metadata's own terms, which used to be re-decided per entity:
    - **`show_in_table`** decides whether a field becomes a column *at all*. `false` ⇒ no column, and therefore no accepted sort. It is the only *flag-driven* gate on either; two explicit policy gates layer on top of it — `excludeFields` removes a field from every output including the detail projection, and `hiddenColumns: "omit"` removes the column (but not the sort) for `hidden` fields.
    - **`hidden`** decides a column's *initial visibility* (`visible: false`, revealable from the column-visibility menu) and **does not affect sortability**. It is a visibility flag, not a permission.
    - **`facet`** decides facet presence, and separately produces `facetFields` — the list entities spread into `friendlyFilters`. **`facet_hidden`** decides a facet's initial visibility (`initiallyVisible: false`). `facet_hidden` on a field that is not a `facet` is inert. Because `facetFields` comes from the `facet` flag alone, a *collapsed* facet is still a legal URL filter, and `facets` and `facetFields` are equal for all eleven resources that collapse. **They differ only for Feature, which is also the only resource that never reads `facetFields`** — it hard-codes `friendlyFilters: ["genome_id", "annotation", "feature_type", "filter"]` in `feature-view/query.ts`. So Feature's six omitted facets (`gene`, `product`, `plfam_id`, `pgfam_id`, `go`, `property`) are **not** legal Feature URL filters. Wiring `featureMetadata.facetFields` into that list would activate six filter names the view has never accepted — a behaviour change, not a tidy-up.
    - **Fields the registry declares array-valued are never sortable**, derived from the Data API registry rather than a hand-maintained per-entity set. `resourceRegistry[resource].fields[name].sortable` (`src/lib/data-api/resources.ts`) is already `!isArrayValued(name) && metadata.sortable !== false`, and it is the same value `validateSort` enforces at the gateway (`src/lib/data-api/validation.ts`), so `DataField.sortable` has exactly one consumer — the registry — and declared cardinality lives in the registry's `multipleFields` table. Strain's per-entity multi-value set was a verbatim copy of that table and is gone. Declared cardinality is what stopped Epitope's `host_name` and Surveillance's `pathogen_test_type` from advertising sortable headers whose sort the gateway rejects.
  - **Residual path — `multipleFields` coverage is incomplete.** It declares cardinality for 7 of the 15 resources; `genome`, `genome_feature`, `protein_feature`, `bioset`, `epitope_assay` and all four child resources (`genome_sequence`, `ppi`, `sequence_feature`, and `genome_feature` again) have no entry. So a multi-valued field outside those seven is caught only if its metadata also says `sortable: false` — which is how `genome_feature.go` is handled (declared `cardinality: "scalar"`, `sortable: false`). Both routes land in the same registry `sortable` answer, so nothing is currently wrong, but the registry is not yet the single source of cardinality truth it is for the seven. Widening `multipleFields` is future work; until then read "array-valued" in this contract as "declared array-valued".
  - **Two per-resource differences remain, and are deliberate rather than accidental — documenting them is the point of this contract, not resolving them by deleting behaviour:**
    - **Feature excludes `facet_hidden` fields from its facets entirely** (`hiddenFacets: "omit"`), because its six high-cardinality hidden facets — `gene`, `product`, `plfam_id`, `pgfam_id`, `go`, `property` — time the upstream combined facet query out. **Strain and every other resource include them, collapsed.** Same flag, different policy, for a real upstream reason. The per-resource facet-composition guard in `collection-field-contract.test.ts` pins the other eleven to "collapse, never omit", so adding `hiddenFacets: "omit"` elsewhere fails loudly rather than silently dropping facets (it would drop 24 for Genome and 17 for Surveillance).
    - **Feature omits a `hidden` field's column entirely** (`hiddenColumns: "omit"`); **Strain and every other resource merely collapse it**, leaving it toggleable. That residual disagreement over what `hidden` means for a column is now written down instead of being re-invented per module.
  - Because `hidden` does not affect sortability (see the `hiddenColumns` gate above), **Feature is the one resource whose sort allowlist is wider than its sortable columns**: its 23 hidden scalar fields keep working sorts (`sort=plfam_id:asc` orders rows correctly) while rendering no column. The invariant therefore runs in one direction only — *every sortable column is in the allowlist*, so the table never offers a header the URL refuses — and `collection-field-contract.test.ts` asserts that a sort with no column behind it can only ever be a `hidden` field.
  - Options exist only for differences the code demonstrates, and the helper branches on no resource name: `excludeFields` (Protein Structure's `sequence`/`alignments`, too large to project anywhere); `hiddenColumns: "omit"` and `hiddenFacets: "omit"` (the two Feature-only policies above); and `adaptColumn` for the link/fallback extras the metadata cannot express (Strain's NCBI nuccore accession fallback, Protein Feature's `patric_id` → `feature_id` fallback and metadata links, Protein Structure suppressing `pdb_id`'s RCSB link so the canonical internal viewer wins). `adaptColumn` shapes columns only — `sorts` comes from the field metadata and the registry, so a profile adapter cannot widen or narrow the URL sort allowlist. `DataField.link` is **not** mapped to `valueHref` automatically — only the three profiles above forward it, exactly as before; see plan item 20B for the metadata link contract. The cross-entity invariants (every accepted sort is registry-sortable and column-backed, every projected field exists in the registry, every facet is registry-facetable) are asserted for all twelve resources against the real validator in `src/lib/views/__tests__/collection-field-contract.test.ts`. (`ResourceField.selectable` was removed as a dead flag every field satisfied unconditionally — projection is now gated only by field existence.)
- `src/components/views/overview-card.tsx` — `OverviewCard` (Card/CardHeader/CardTitle/CardContent shell) and `OverviewField` (a single `<dt>`/`<dd>` pair, omitted when unavailable) plus the value-availability/format helpers `isOverviewValueAvailable`/`formatOverviewValue`, shared by the six entity `*-overview.tsx` pages (Genome, Feature, Epitope, Experiment, Surveillance, Serology). Availability treats `null`/`undefined`/`""`, an empty array, an array with no primitive items, and an object that serializes to no meaningful JSON (`{}`, `[]`, or a value `JSON.stringify` cannot represent) as unavailable — `0` and `false` remain available — so a field never renders an empty `<dd>` under a populated `<dt>`. A *populated* object renders as its real JSON (as Experiment's `additional_metadata` always did), never stringified to `"[object Object]"` the way Genome and Epitope used to. `OverviewField` accepts either a raw `value` (formatted via `formatOverviewValue`) or `children` for entity-specific content (a link, a multi-item link list) alongside an `available` override for cases where visibility depends on logic other than the raw value (e.g. a recognized taxon ID shape). `OverviewCard` only supplies the card shell; each page still builds its own `<dl className="grid gap-4 sm:grid-cols-2">` (or its own "No data available." fallback for Surveillance/Serology's per-section empty state), so section layout, links, feature counts, coordinates, and date formatting (`formatSourceDate`/`formatSerologyDate`) stay local to each page as before.
- `src/components/views/` — generic `ResourceCollection`, its `useResourceCollectionActions` action boundary, `ResourceWorkspace`, controlled resource filtering, export formatting, and `EntityViewShell` composition. `EntityViewShell` reuses the organism landing navigation and content-frame primitives so resource views retain the Taxonomy layout across desktop and mobile. Profile-backed Taxonomy, Genome, Feature, Epitope, Surveillance, Serology, Strain, Domains and Motifs, Protein Structures, and Experiment adapters support canonical collections and scoped member tabs; Taxonomy contributes immutable lineage scope for those collection tabs, while Feature retains cross-core queries where required. Surveillance and Serology keep backend `id` as row identity and resolve public members by `sample_identifier` plus their optional discriminator (`pathogen_test_type` or `test_type`), presenting a choice when the sample alone is ambiguous. Strain and Domains and Motifs are list-only and use backend `id`; their selected-record details stay in the collection. `src/hooks/views/` owns TanStack Query collection/detail behavior, URL synchronization, and local explicit/all-matching selection state.
- Genome routes are implemented: `/genome` is a multi-resource collection view, and `/genome/[genomeId]` is the `genome_id` member. The collection preserves its Genome RQL while switching among Genomes, Sequences, Features, Proteins, Protein Structures, and Domains and Motifs; tabs without a validated selected-genome query contract remain capability-gated. Member Features, Proteins, and Domains and Motifs use exact `genome_id` scopes.
- Feature routes are implemented: `/feature` is the focused `genome_feature` collection, and `/feature/[featureId]` uses canonical `feature_id`. Legacy `fig|...` PATRIC IDs resolve through `patric_id` and permanently redirect to the canonical member. Overview, exact-feature Interactions, and exact-feature Domains and Motifs are available; unsupported tabs remain capability-gated.
- Epitope routes are implemented: `/epitope` is the focused `epitope` collection, and `/epitope/[epitopeId]` provides Overview and an exact-epitope `epitope_assay` collection. The Taxonomy Epitope tab uses the same collection profile with immutable lineage scope.
- Surveillance and Serology routes are implemented as focused collections plus compound sample members. Their Taxonomy tabs reuse the same profiles with immutable lineage scope; public member identity remains separate from backend row identity.
- Strain is implemented as a focused list-only `/strain` collection. It has no member route; selection-driven details stay in the collection, and the Taxonomy Strains tab reuses the same profile with immutable lineage scope and local loaded-row keyword filtering.
- Collections whose row selection resolves to a set of service- or group-ready IDs share `CollectionSelectionActions` (`src/components/views/collection-selection-actions.tsx`) for the COPY ROWS, SERVICES, GENOMES, and GROUP sidebar actions, along with `CollectionCopyDialog` and `SelectionServiceChooser`. `idField` names the row field and `idKind` says what it holds: Genome IDs (Strain via `genome_ids`, Genome and Sequence via `genome_id`) or Feature IDs (Feature via `feature_id`). `idKind` picks the chooser's service set (BLAST/Viral Genome Tree/Viral MSA for genomes; BLAST — which asks Query or Source first — /Gene Tree/HA Subtype Numbering Conversion for features) and the workspace group the selection writes to (`groupTargetByKind`: Genome Groups or Feature Groups, both via `createIdGroup`). Domains and Motifs, Protein Structure, SFVT, Epitopes, Serology and Surveillance use the same component with `copyAndServicesSelectionActionIds` and `hasSelectableServices={false}`, so their SERVICES button opens the chooser's empty state (as the Taxa Tree tab does) instead of resolving IDs — legacy runs no service from those tabs. Experiments and Biosets go further with `servicesOnlySelectionActionIds`, because legacy also leaves COPY ROWS out of those two containers' `validContainerTypes`. Interactions add `interactionSelectionActionIds` (COPY, SERVICES, FEATURES, GROUP) and pass `idField: ["feature_id_a", "feature_id_b"]` — `idsFromRows` pools several fields, so one row contributes both interactors to the FEATURES list URL (`featuresHrefFromIds`) and to the Feature Group, matching legacy. `src/lib/views/collection-selection.ts` holds ID extraction and two distinct kinds of ceiling: row ceilings (`selection*MaxRows`) bound the pre-fetch, while ID ceilings (`selection*MaxIds`) are enforced *after* `idsFromRows` flattens and de-duplicates, because one Strain or Interaction row can contribute many IDs. The list ceilings derive from `maxRqlInValues` (the Data API's 500-value `in(...)` limit, exported from `src/lib/data-api/rql.ts`), which `genomesHrefFromIds` and `featuresHrefFromIds` also apply by returning `null` rather than truncating; `selectionListMaxUrlLength` stays the tighter bound for long Feature IDs. `useResourceCollectionActions` picks the resource's action set from `selectionActionsConfigByResource` and dispatches the actions the component does not own (DWNLD, GENOME, FEATURE, FEATURES, STRUCTURE, EPITOPE, SEROLOGY, SRVLNCE, EXPRMNT, BIOSETS) through `onOtherAction`, passing their disable reasons in via `disabledActions` and any that the shared config disables by default in via `extraEnabledActionIds` (Sequence uses it for FEATURES). Actions still waiting on a later PR keep the `notReady` tooltip: FASTA and Browser on Sequences, FASTA and ID MAP on Features, VARIANT TYPES on SFVT, MAP on Surveillance, FASTA on Interactions, BIOSETS on Experiments (it stays live on Biosets, where `extraEnabledActionIds` re-enables it). Multi-consumer pieces stay resource-neutral in name; single-consumer ones (such as `TaxonomyServiceChooser`) keep their resource prefix.
- Everything a collection's action bar knows about a *specific* resource lives in `useResourceCollectionActions` (`src/components/views/resource-collection-actions.tsx`), not in `ResourceCollection`: the `selectionActionsConfigByResource` and `enabledActionsByResource` tables, `resolveActionTargets` (the identifiers and member destinations a row selection resolves to — Genome, Feature, Sequence, Epitope, Experiment, Structure, the detail row's own href, and the Bioset experiment IDs), `resolveDisabledActions` (the per-resource disabled-reason policy), the Taxonomy and Bioset workflows that must resolve IDs over the network before they can navigate, and the `TaxonomyServiceChooser`. The shell keeps querying, URL and filter state, loaded-keyword behaviour, table and detail rendering, and export; it passes nine options in — `profile`, `selection` (count, raw and displayed selected IDs, all-pages flag, matching total, and a `rowById` lookup backed by the shell's across-pages row memory), `detail`, `activeId`, `columnVisibility`, `resolveActionRows`, `resolveAllMatchingRows`, `onExportSelection`, `onError` — and takes back only an error message, which it renders in its own "Could not complete action" alert. `resolveAllMatchingRows` is the shell's one door onto "every row matching the current query, with these fields", so scope, keyword, sort and keyword mode stay in one place and the two all-pages workflows ask for a column instead of rebuilding the query. Adding a resource therefore means extending the tables and the target/disabled-reason functions in that one file, plus its parameterized zero/one/multiple/all-pages matrix in `src/components/views/__tests__/resource-collection-selection-actions.test.tsx`; the generic query, export and table code is untouched and mentions no resource by name. Plan item 21 split the former all-in-one `resource-collection.test.tsx` by behaviour: that file now holds only generic collection/export/filter/detail tests (plus the shared error-presentation contract), and `resource-collection-{selection,taxonomy,bioset,navigation}-actions.test.tsx` hold the resource-specific action-bar tests — selection enabling/disabling and the cross-resource matrix, the Taxonomy pop-up/race workflow, the Bioset experiment-resolution workflow, and single-row member-navigation destinations, respectively. A typed `useResourceCollection` result builder shared by all of these (and by `resource-child-collection.test.tsx`) lives in `src/components/views/__tests__/fixtures/resource-collection-result.ts`. Their `SearchActionBar` fake is likewise one shared factory, `createSearchActionBarFake` in `src/components/views/__tests__/fixtures/search-action-bar-fake.tsx`: it renders a disabled action (gated on `enabledActions`, per the real bar's `actionConfig`, or carrying a truthy `disabledActions` reason) as a present, disabled `<button>` — matching `search-action-bar.tsx`'s own `isDisabled`, which never removes a button from the DOM — rather than hiding it, so a test asserts `toBeDisabled()` instead of absence.
- **It is a hook returning two slots (`{ actionBar, actionDialogs }`), not a component, and that is load-bearing.** `ResourceWorkspace` renders its `actionBar` under structurally different parents either side of the `md` breakpoint — `div[data-layout="stacked"] > aside` versus `ResizablePanelGroup > ResizablePanel > aside` — and switches between them from a live `matchMedia` listener, so **any state held inside that slot is destroyed by a window resize or a tablet rotation** (`isNarrow` also starts `false` and flips in an effect, so a narrow viewport remounts the slot on every page load). The Taxonomy launch resolves IDs over the network before it can navigate, so state kept in the slot would mean a resize mid-resolution silently dropping the launch — no chooser, no error, no spinner. Running as a hook puts `loadingActionIds`, the overlap ref and the chooser's state in the shell's own instance, and the shell renders `actionDialogs` at `<section>` level, outside `ResourceWorkspace` entirely, so the chooser also survives the collection-error branch. The non-Taxonomy pop-up actions need none of this: they hold a direct `resultsWindow` reference, so an unmount cannot cancel the navigation. `src/components/views/__tests__/resource-collection-actions.test.tsx` is the regression guard — it uses the *real* `ResourceWorkspace` and `SearchActionBar` and drives the `matchMedia` `"change"` listener across the breakpoint mid-resolution. Anything new that puts state in that slot owes itself the same treatment.
- Loaded-mode keyword search (`keywordMode="loaded"`, used by the Taxonomy tabs and by the Genome and Feature member tabs) filters the already-fetched page client-side and deliberately never reaches `state.keyword`, so it is not part of the request. `ResourceCollection` owns the one export implementation for both itself and `ResourceChildCollection` (plan item 14 deleted the child's duplicate serializer): its `exportRows` requests every profile column when a loaded keyword is active, filters with `matchesLoadedKeyword`, and projects the requested fields back down before calling `downloadResourceExport`/`serializeResourceRows` in `resource-export.ts`. Selected-ID exports are already exact and stay unfiltered. `ResourceCollectionProfile.exportFileName` is the one sanctioned override point: `ResourceChildCollection` sets it to the tab's label so a child export keeps naming its download after the tab (e.g. "Domains and Motifs") instead of the shared resource id every other `downloadResourceExport` caller uses, and it also carries `serverKeywordMode` through unchanged when a supplied or canonical profile defines it (only `taxonomyCollectionProfile` does today).
- Interactions (`src/components/interactions/`) presents one PPI dataset two ways, so both representations share one data contract. `InteractionsSubviewShell` strips any URL fragment from the scoping RQL once and hands the same predicate *and* the same keyword text to `ResourceChildCollection` (a collection request) and to `InteractionsGraph` (a bulk-row request through `useInteractions`), both over `/api/data/ppi`. The shared keyword is therefore a server-side search on both sides: `ResourceChildCollection` accepts a controlled `keywordValue`/`onKeywordChange` pair and feeds it into `state.keyword` instead of filtering the loaded page, which is why the Interactions Table is not a `keywordMode="loaded"` consumer. Because that keyword is a request predicate for two mounted views, **both** boxes debounce before committing — `ResourceFilterBar` for the Table and `GraphToolbar` for the Graph — sharing `keywordDebounceMs` from `src/components/filterbar/keyword-search.tsx`; `KeywordSearch` itself reports every input event, so any consumer that turns its value into a request owes it a draft and a timer. Graph rows are validated by `ppiGraphRecordSchema` (`src/lib/interactions/schema.ts`), which requires both interactor endpoints, and the graph requests `interactionsGraphRowLimit + 1` rows so it can report truncation rather than silently capping. It reads no `NEXT_PUBLIC_DATA_API`: configuration and request failures arrive as a rejected query and render the standard error state.
- Interaction scoping predicates live in `src/lib/views/child-resources.ts`. Feature and Genome match either interaction endpoint (`feature_id_a`/`_b`, `genome_id_a`/`_b`), because a PPI row does not say which side carries the scoped organism. Taxonomy stays A-side only: it resolves a lineage through the Genome relationship join and the RQL contract accepts `to(genome_id_a)` alone for `ppi` (`src/lib/data-api/rql.ts`), so symmetry there needs a contract change rather than a wider predicate.
- `SearchActionBar`'s `actionConfig` renders in array order, which follows the legacy action bar (FEATURE before GENOME, GROUP last), so every collection's sidebar matches its legacy tab. Legacy's SUBSYSTEMS and PATHWAYS actions are intentionally absent.
- Domains and Motifs is implemented as a focused list-only `/domains-and-motifs` collection backed by `protein_feature`. Its Taxonomy tab uses the same profile with a cross-core Genome lineage scope and intentionally does not exclude Deprecated genomes; Genome and Feature member tabs use exact parent scopes.
- Protein Structures is implemented as a profile-backed `/protein-structure` collection and an id-less member selected by `?accession=` or `?path=`. Accession mode accepts up to 10 PDB or AlphaFold accessions and enriches PDB entries from `protein_structure` when metadata is available; workspace mode accepts one mutually exclusive workspace path. Mol* tries ordered sources until one loads: a BV-BRC `file_path` through `/api/structure/[...path]`, then an AlphaFold model inferred from the accession or UniProt metadata, then RCSB for PDB IDs. Workspace files load through `/api/workspace/view/...`. The same collection profile powers exact Genome scopes, Feature matches across PATRIC ID/sequence MD5/UniProt/PDB identifiers, and Taxonomy's non-Deprecated lineage join.
- Experiment routes are implemented: `/experiment` provides Experiments and Biosets tabs; the Biosets tab resolves the matching Experiment IDs first so Experiment filters and keyword searches scope its `bioset` collection. `/experiment/[experimentId]` preserves the positive digit-string `exp_id` and provides Overview and an exact-experiment `bioset` collection. Biosets have no top-level route. Genome and Taxonomy Experiment tabs reuse the profile with immutable exact or lineage scope.
- Taxonomy routes are implemented: `/taxonomy` is the focused `taxonomy` collection and `/taxonomy/[taxonId]` retains the organism/taxon member shell. Taxon actions open canonical overview, Genome, and Feature destinations; the Services action prefills BLAST's supported Taxon-list database input.
- Domain schemas, profiles, query builders, columns, and tabs stay with the route rather than entering a universal singular-view dispatcher.
- Organism landing pages (`src/app/organisms/(all|bacteria|viruses)`) are tabbed, driven by a per-organism `_config.ts` (`OrganismLandingConfig` in `src/components/organisms/types.ts`) + shared components in `src/components/organisms/`.

- Tab visibility policy: `src/app/api/taxon-view/tab-policy` + `docs/taxon-view-tab-visibility.md`.
- Phylogeny renderers, local Nextstrain datasets, deployment, and licensing: `docs/phylogeny-integration.md`.

## Detail panel metadata links (search results)

`src/components/detail-panel/info-panel.tsx` (the search variant, `renderSearchInfoPanel`) renders per-tab metadata fields from `src/constants/datafields/*` for the search results detail panel — a separate rendering path from the `*-view` collection/member pages above, and from their table columns.

- **One classification rule for every link shape.** `classifyHref(href)` returns `"internal"` (an unambiguous same-origin path — `startsWith("/")` and explicitly not a protocol-relative `//host`), `"external"` (an absolute `http(s)` URL, opened in a new `noopener`-isolated tab), or `"unsafe"` (anything else — a bare `//host`, a `javascript:`/`mailto:`/other non-http(s) scheme, or a string that is neither). `"unsafe"` renders nothing at all — no anchor, no `Link` — rather than guess. Scalar, array, and `linkType: "button"` fields all go through the same `renderMetadataLink`/`renderMetadataLinkButton` helpers, so a link's shape never changes its routing or security contract. There used to be a fourth, inconsistent path here: scalar links were rebased onto a hardcoded `https://www.dxkb.org` origin and always rendered as external new-tab anchors, so a canonical relative link like `/genome/{value}` left the current deployment (staging, a preview, localhost) instead of navigating internally; and the original two-way `isExternalHref` check treated "not external" as "therefore internal", which would have handed a protocol-relative `//host` or a `javascript:` URI straight to `Link` with no `target`/`rel` isolation (latent only — no current template can produce one, since `resolveLink` always `encodeURIComponent`s row-supplied segments — but the boundary needed to hold regardless of today's data). Plan item 20B removed the origin rebase and unified all three shapes onto `classifyHref`; a same-day review added the third `"unsafe"` outcome.
- **`detail-key-value.tsx`'s `DetailField` carries no `href`.** Every link-bearing field is built as `render: () => ReactNode` in `info-panel.tsx`, which owns all routing/classification concerns; `DetailKeyValueTable` stays a pure presentational renderer (plain value, date formatting, or a supplied `render()`) with no knowledge of internal-versus-external destinations. `DetailKeyValueTable` has exactly one consumer (`info-panel.tsx`, via `DetailPanel.KeyValueTable`), so this is a safe, complete contract change rather than a partial one.
- **`resolveLink(template, row, fallbackField)`** fills `{placeholder}` tokens against the row. `{value}` is a sentinel that never matches a real row key, so it always falls back to the field's own value; a real field name like `{genome_id}` matches the row directly (row-aware — e.g. `genome_feature.genome_name`'s link points at `/genome/{genome_id}`, not its own value). It returns `undefined` — rejecting the link outright, so the field falls back to plain-text rendering — when any placeholder has no resolvable primitive value, rather than emitting a URL with a missing or literal `{...}` segment.
- **Ruling: `enableRowLinks` and metadata links are independent, by design.** `enableRowLinks` (`genome-resource-collection.tsx` and its six siblings, `resource-collection.tsx:174`) governs only whether a collection table row click navigates to the entity's member page. It has no interaction with `DataField.link` or this detail panel: the Taxa Tree tabs that set `enableRowLinks={false}` (`src/components/organisms/taxon-views/*.tsx`) do so as a deliberate legacy-parity call about row navigation, and it neither activates nor suppresses a metadata link. This was previously an implicit, undocumented divergence; it is a decision now, not an oversight.
- **Datafields audit (item 20B).** Swept `src/constants/datafields/*` for legacy `/view/*` routes, hardcoded production origins, and plain-http targets. Fixed: `strain.taxon_id`, `genome_feature.taxon_id`, and `epitope.taxon_id` converged from the stale `/view/Taxonomy/{value}` onto `/taxonomy/{value}` (matching Protein Feature's already-canonical destination); `genome.contigs` moved from a hardcoded `https://www.dxkb.org/view/Genome/{genome_id}?activeTab=sequences` to the row-aware internal `/genome/{genome_id}?tab=sequences` (the genome-view `sequences` tab — the old `activeTab` param was never read by the new page anyway, since `src/proxy.ts`'s internal-redirect step only rewrites `?view=` to `?tab=`, not `?activeTab=`); `protein_feature.refseq_locus_tag` moved from plain `http://` to `https://`. `genome_sequence.sequence_id`'s legacy `/view/FeatureList/?and(eq(annotation,PATRIC),eq(sequence_id,{value}),eq(feature_type,CDS))` was rewritten onto `/feature?rql=and(eq(annotation,PATRIC),eq(sequence_id,{value}),eq(feature_type,CDS))` — not a guess: `src/proxy.ts`'s live `/view/*` redirect (`mapLegacyViewPath`, matcher includes `/view/:path*`) maps that exact legacy path+query to this exact `/feature?rql=...` form (`FeatureList` → segment `feature`, a query string with no top-level `name=` pair is forwarded verbatim as `rql=`), and `validateRql("genome_feature", "and(eq(annotation,PATRIC),eq(sequence_id,X),eq(feature_type,CDS))")` round-trips unchanged through the real RQL validator — the same `annotation`/`feature_type` pairing `feature-view/query.ts`'s `proteinFeatureRql` already uses for "Proteins" filtering. This item's scope is the detail panel only, per plan item 15's boundary — no `DataTableColumn.valueHref` (table-column link destination) was activated, and both of item 15's named carve-outs (Strain's NCBI accession fallback, Protein Feature's `patric_id` fallback) are untouched. But two of the fixes above land on fields Strain's and Protein Feature's `adaptColumn`s (`strain-view/fields.ts`, `protein-feature-view/fields.ts`) already forward verbatim to `valueHref` — `strain.taxon_id` and `protein_feature.refseq_locus_tag` are each a single shared `DataField` object read by both the detail panel and that resource's table column. Correcting the stale route/scheme at that one shared source therefore corrects both surfaces' `valueHref` too, as a deliberate and necessary consequence of fixing the datafield, not a new activation — `collection-field-contract.test.ts`'s Strain adapter test was updated accordingly.

## Services pattern

- Each bioinformatics service is a form page under `/services/`
- Forms use TanStack Form (`@tanstack/react-form`) + zod validation
- Submission: `useServiceFormSubmission` hook → `submitServiceJob()` → `AppService.start_app2`
- `ServiceDebuggingProvider` wraps service layouts; enables a debug mode that shows params instead of submitting

## Rerun pre-fill pattern

- `useRerunForm<T>()` reads job params from `sessionStorage` (keyed by `?rerun_key=`) and returns `{ rerunData }`
- Pre-fill is auto-applied via the hook's declarative options (`fields`, `libraries`, `syncLibraries`, `onApply`); the hook self-manages one-shot application internally
- The sessionStorage entry is intentionally NOT consumed on read because React rendering may remount the form; consume-on-read could null out a subsequent mount
- Library reconstruction helpers in `src/lib/rerun-utility.ts`:
  - `buildPairedLibraries(rerunData, getExtra?)` — paired-end libs from `paired_end_libs`
  - `buildSingleLibraries(rerunData, getExtra?)` — single-end libs from `single_end_libs`
  - `buildSraLibraries(rerunData)` — SRA libs from `srr_libs` with `srr_ids` fallback
  - Pass a `getExtra` callback to merge service-specific fields (e.g. `platform`, `interleaved`)

## Data fetching

- TanStack Query for all async state (client-side)
- View collections and member detail panels use `src/hooks/views/` over the `DataRepository` boundary in `src/lib/data-api/`; components do not parse upstream wire formats.
- Custom hooks in `src/hooks/services/workspace/` wrap workspace API calls
- `src/lib/api/client.ts` uses credentialed fetch; only the app-specific `session_expired` code triggers one hard reload, while ordinary upstream 401 responses remain API errors
