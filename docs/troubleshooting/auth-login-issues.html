Sign-In 404 & Phantom Verification

Two unrelated failures that hit the login flow back to back. One is local to your dev machine and needs no code. The other is a real bug in how the server talks to BV-BRC — fixed, but not yet merged.

Found 17 Aug 2026 Branch DXKBCORE-221 Status both fixed, uncommitted

If your sign-in POST 404s: your dev server's router went stale. Restart it — nothing is wrong with the code.

If you sign in but get a "verify your email" banner, a dead resend link, and get logged out on refresh: that's Cloudflare blocking the server's profile lookup. Needs the code fix below.

Issue 1 Local dev only No code change

POST /api/auth/sign-in/email returns 404

You click submit and the request 404s. The route file exists, it's committed, and it looks fine — because it is fine. The request never reached it.

How to confirm it's this

Two tells. First, the 404 body is Next.js's HTML error page, not a JSON error from the handler — so nothing in the app ran. Second, and quicker: 

# the route only exports POST, so send it a GET
curl -o /dev/null -w '%{http_code}' localhost:3019/api/auth/sign-in/email

405  → route is registered, your problem is elsewhere
404  → router never registered it. This issue.

A registered route rejects the wrong method with 405. Only an unregistered path gives 404.

What was actually wrong

Turbopack's dev cache had desynced. The route was compiled on disk, its chunks existed, and it was listed in the route manifest — but the running router had never registered it. Nested routes were hit and flat ones weren't: both sign-in/email and sign-up/email 404'd while profile and forget-password worked. Sign-out is now a redirecting Server Action rather than an API route.

Fix
  • Right now: touch the route file to force an HMR rebuild, or restart the dev server.
  • If it comes back: rm -rf .next/dev && pnpm dev for a clean rebuild.
  • Root cause, now pinned: stray package-lock.json files in parent directories were making Next infer /home/<user>/ as the workspace root, which breaks file-watching. turbopack.root is now set explicitly in next.config.ts. If you saw a "Next.js inferred your workspace root" warning at startup, that was this — it should be gone.
Issue 2 Affects everyone Code fix

False "verify your email" banner, dead resend link, logout on refresh

Sign-in succeeds. Then three things go wrong at once, and they look like three separate bugs:

  • A red "Unverified Account Email" banner appears — even for accounts that are verified.
  • The "click here" resend link does nothing visible.
  • Refreshing the page logs you out.

All three are one cause: Cloudflare is blocking the server's calls to the BV-BRC user service.

Why

Node's built-in fetch sends User-Agent: node by default. Cloudflare in front of user.patricbrc.org answers that with a 403 bot challenge — an HTML page reading "Just a moment…" — instead of the API response.

Why it's hard to spot

Only some endpoints are challenged, and /authenticate isn't one of them. That's exactly why sign-in works and everything after it breaks.

Same token, same host, from Node's fetch
Endpoint Status Result
POST /authenticate 401 Real API response — sign-in works
GET /user/<id> 403 Cloudflare challenge
POST /verify 403 Cloudflare challenge
The trap

You cannot reproduce this with curl. Identical request, three different user agents: 

bare (as the app does)  → 403  Cloudflare challenge
with curl UA            → 200
with browser UA         → 200

Probe the endpoint by hand and it looks perfectly healthy. A 403 with an HTML body is a bot challenge; a 403 with a JSON body is the API.

How one 403 caused all three symptoms

  • The banner: isVerified treats an authenticated account as unverified only when email_verified is explicitly false. A missing value satisfies user.email_verified !== false, so it does not explain the banner.
  • The dead link: it calls POST /verify — also challenged. The click handler discards its result, so the failure was silent.
  • The logout: the former browser session revalidation called the same profile endpoint and treated any error as "session invalid". The server-first flow now preserves cookies for network, timeout, malformed-response, rate-limit, and 5xx failures.
Fix

Send an explicit User-Agent on every server-side identity request to BV-BRC. The identity adapter applies the header in its shared request helper, so authentication, registration, profile, verification, and password operations all use the same behavior:

src/lib/auth/server/adapters/bvbrc-identity.ts — shared request helper and all identity-service calls

The identity adapter owns both profile validation and the explicit user-agent policy. Inspect its request helper when diagnosing stripped headers or BV-BRC identity failures.

Verified

Server-rendered getCurrentUser() now receives a full profile with email_verified: true, and /api/auth/profile returns 200. Regression tests assert that every identity request's User-Agent equals serverUserAgent and fail if the header is stripped.

What to do: if you only have the 404, restart your dev server — you don't need the code change. If you're seeing the verification banner or getting logged out on refresh, you need the User-Agent fix; it isn't committed yet, so pull once it lands on DXKBCORE-221 (branched from dev).

Resend-verification is exposed through the named client action and should surface failures to the user.
