# Architecture (deep reference)

On-demand companion to `AGENTS.md`. Read this when you need the full module map; the `AGENTS.md` summary + on-pattern recipes cover most day-to-day work.

**DXKB V2** is a Next.js 16 app (App Router) serving as a Disease X Knowledge Base — a bioinformatics platform for genomics, metagenomics, and viral research.

## App Router structure (`src/app/`)

Route groups `(…)` are organizational and do NOT appear in the URL.

**Dynamic route params are not delivered in one encoding.** Next hands a page
or layout component `encodeURIComponent(value)` (via `getDynamicParam()`),
while `generateMetadata` receives the route matcher's decoded value, and
route handlers and `searchParams` are decoded everywhere. A page component
that forwards its param as data therefore sends a value one encoding level
too deep. That 404'd every Surveillance/Serology identifier containing a
character `encodeURIComponent` escapes, doubly encoded every workspace file
URL the standalone structure viewer requested, and doubly encoded the
`/workspace/home/**` and `/workspace/shared/**` redirect targets. A page
component's param must be read back exactly once: use `readRouteParam` /
`readRouteParamSegments` in `src/lib/views/route-params.ts`, whose doc comment
carries the Next-internals citation and the per-entry-point rules. Do not
decode in `generateMetadata` or in a route handler — both already receive the
decoded value, and decoding there corrupts an identifier containing a literal
`%xx`. (Four pages under `workspace/[username]/**` and `workspace/public/**`
predate the helper and do the same single decode through `safeDecode`; that is
correct, just older. `workspace/[username]/page.tsx` is no longer among them —
it reads through `readRouteParam` now.)

- `/` — Public home page (search, news, statistics)
- `(auth)/` — `sign-in`, `sign-up`, `forgot-password`
- `(footer)/` — static content pages (about, faq, news, privacy-policy, team, etc.)
- `(views)/` — BV-BRC data view pages: `genome`, `taxonomy`, `strain`, `feature`, `epitope`, `experiment`, `serology`, `surveillance`, `protein-structure`, `domains-and-motifs`. The registry supplies route metadata; production views use explicit per-route composition (see **Views & organism landing**)
- `/organisms/(all|bacteria|viruses)/...` — organism landing pages (tabbed; driven by `_config.ts` + view registry)
- `/workspace/...` — workspace file browser. Route shapes: `/workspace/[username]/home/[[...path]]`, `/workspace/[username]/[folder]/[[...path]]`, `/workspace/home/[[...path]]`, `/workspace/shared/[[...path]]`, `/workspace/public/[username]/[...path]`, `/workspace/workshop`
- `/services/(genomics|metagenomics|phylogenomics|protein-tools|utilities|viral-tools)/...` — service submission forms (route groups as categories)
- `/search/` — Global search
- `/jobs/` — Job monitoring
- `/settings/` — user settings
- `/viewer/structure/` — standalone workspace-backed 3D protein structure viewer
- `/api/auth/...` — Custom auth API routes
- `/api/services/...` — Proxied service API routes
- `/api/workspace/...` — Proxied workspace API routes
- `/api/data/[resource]` — validated, rate-limited same-origin gateway to allowlisted BV-BRC Data API resources
- `/api/taxonomy-tree/[operation]` — rate-limited same-origin boundary for the Taxa Tree's `children` and `child-counts` reads (see "Taxa Tree route contract")
- `/api/structure/[...path]` — validated same-origin proxy for BV-BRC-hosted structure files
- `/api/taxon-view/tab-policy` — tab-visibility policy for views (see `docs/taxon-view-tab-visibility.md`)
- `/api/e2e-mock/[...path]` — loopback backend mock used only by the Playwright suite, guarded by `E2E_MOCK_ENABLED=1`. Its populated fixtures come from `src/lib/e2e-fixtures/records.ts` (dependency-free typed canonical records) + `envelopes.ts` (transport-specific Solr/gateway/JSON-RPC wrapping), the single source of truth shared with the browser-side mock in `e2e/fixtures/overrides/catchall.ts`. Only those three directories may import `src/lib/e2e-fixtures/**` (a `no-restricted-imports` zone plus `src/__tests__/e2e-fixtures-import-boundary.test.ts` pin the allowlist). Dispatch is **fail-closed**: every served path / RPC method is named in the module and anything else gets a diagnostic `400`, never an empty success — see `e2e/README.md` for the served set and for the fixture-composition breakdown (empty fallback vs. named resource scenario bundles vs. the a11y-only aggregate)

## Auth system (`src/lib/auth/`) — server-first identity

- `client.ts` — concrete browser functions for retained `/api/auth/*` mutations and profile operations
- `provider.tsx` — `<AuthBoundary user={user}>`, `useAuth()` derived identity, and `useAuthActions()` mutations
- `routes.ts` — protected page classification used by the proxy; protected route-group layouts enforce the policy authoritatively through `server/page-auth.ts`
- `types.ts` — browser-safe `AuthUser`, upstream `UserProfile`, credentials, sessions, and `Result` types
- `server/actions.ts` — named auth operations such as `signIn`, `signOut`, `startImpersonation`, and cached `getCurrentUser`
- `server/session.ts` — sole owner of HttpOnly session and SU backup cookie reads/writes
- `server/cookies.ts` — Edge-safe cookie names and optimistic cookie-presence check
- `server/route.ts` — authenticated route wrapping and direct session reads for routes and Server Components
- `server/page-auth.ts` — authoritative protected-page redirect helper used by the narrowest protected layouts; it validates `getCurrentUser()` and preserves the proxy-forwarded path and query
- `server/adapters/bvbrc-identity.ts` — named BV-BRC identity protocol calls

Notes:

- This is custom BV-BRC authentication, not Better Auth. Server rendering validates cookies through `getCurrentUser()` and passes the browser-safe user into `<AuthBoundary>`; the browser does not fetch a session on mount and never receives the BV-BRC token.
- `src/proxy.ts` delegates page classification to `isProtectedPagePath()`. It optimistically checks cookie presence and forwards the server-visible path plus query to protected layouts; `requireCurrentUserOrRedirect()` in `server/page-auth.ts` validates the user before protected content renders. URL fragments cannot be preserved because browsers do not send them in HTTP requests.
- The active session cookies are `bvbrc_token`, `bvbrc_user_id`, and optional `bvbrc_realm`, all HttpOnly, SameSite Strict, path `/`, and Secure in production. Explicit sign-out is a redirecting Server Action, not an `/api/auth/sign-out` route.
- `/api/auth/*` wire contracts are documented in `docs/auth-api.md`. Every auth failure uses `{error, code}`.

## Backend communication

- `JsonRpcClient` (`src/lib/jsonrpc-client.ts`) — all backend calls use JSON-RPC 2.0 over HTTP POST; requires `APP_SERVICE_URL` env var
- `AppService` (`src/lib/app-service.ts`) — job management: enumerate/query/kill jobs, submit services via `AppService.start_app2`
- `WorkspaceApiClient` (`src/lib/services/workspace/client.ts`) — workspace CRUD operations
- `src/lib/data-api/` — typed Data API resource registry, validation, RQL serialization, server/browser repositories, normalized response types, and TanStack Query option/key factories. Browser view code uses `/api/data/[resource]`; upstream URLs and BV-BRC tokens remain server-only.
- `src/lib/data-api/server-policy.ts` — `resolveServerDataRepository()` is the single place the Data API's server-side auth, configuration and cache policy is decided, shared by all three server entry points that need a `ServerDataRepository`: the page factory below, the gateway route, and the Taxa Tree route. It resolves `DATA_API_URL`/`NEXT_PUBLIC_DATA_API`, reads the session, builds the repository, and returns it alongside a `sharedCache` flag. **Cache policy: members only.** A `readScope: "member"` read (one row addressed by one identifier, so a bounded key space and a high hit rate) is `force-cache` with a 300-second revalidation window *when the caller is anonymous and the process is not in an E2E run*; every `readScope: "query"` read (collection, selected rows, export, ranged) is `no-store` even when anonymous, because its URL carries filters, sort, page and keyword and would fill Next's data cache with near-unique entries at a low hit rate. An authenticated session or `E2E_MOCK_ENABLED=1` forces `no-store` for either scope. The base-URL check runs before `readSession()` so a configuration failure never depends on a session lookup succeeding first, and the throw is always `DataApiError(…, 500, "not_configured")` — a discriminator callers rely on to tell a deployment problem apart from a `readSession()`/`cookies()` failure, which must propagate untouched. The client-facing message and the optional operator-facing `console.error` line are supplied *by the caller*, because only the caller knows which entry point is unconfigured and how much of the reason its audience may see. Neither this function nor the factory is wrapped in React `cache()`: memoizing repository construction would share one repository across every caller in a single render pass.
- `src/lib/data-api/server-repository.ts` — `createServerDataRepository({ readScope, fetch? })` guards itself with `import "server-only"` and is the single factory every `src/lib/*-view/server.ts` entity-lookup module (`genome`, `feature`, `epitope`, `surveillance`, `serology`, `experiment`, `protein-structure`) uses to build its `ServerDataRepository`. It is a thin wrapper over `resolveServerDataRepository` and adds exactly one thing: the client-facing wording `"DATA_API_URL is not configured."`, which names the env var on purpose because nothing returns this string to an arbitrary caller. `readScope` is required, not defaulted, because the five `"member"` callers (`genome`, `feature`, `epitope`, `experiment`, `protein-structure`) are cacheable while anonymous and the two `"query"` callers — the `collection`-backed compound lookups `surveillance` and `serology` — are not; a default would have let a future collection caller silently inherit the member cache. Entity lookup, alternate IDs, compound resolution, parsing, and error semantics stay in each calling module. A different, cross-cutting set of six — the scalar-ID modules `genome`, `feature`, `epitope`, `experiment`, `surveillance`, `serology` — let the missing-config error propagate (each keeps its own `cache()` wrapper around its own exported lookup) so Next redacts the message in production. Note the two groupings are not the same partition and are not the same size: four `"member"` callers plus both `"query"` callers propagate, because how a module surfaces a configuration failure is unrelated to whether its reads are cacheable. `protein-structure-view/server.ts` differs on purpose: it resolves an array of accessions, so it is not wrapped in `cache()` at all, and it catches the factory's error — narrowing on exactly `error instanceof DataApiError && error.code === "not_configured"` and rethrowing anything else — to map it onto its existing per-accession `error` field with a generic message plus a `console.error` carrying the env var detail, instead of rendering the variable name into the response.

### Data API gateway contract

- Supported resources, each paired with its stable ID: `taxonomy` → `taxon_id`, `genome` → `genome_id`, `genome_amr` → `id`, `genome_feature` → `feature_id`, `epitope` → `epitope_id`, `epitope_assay` → `assay_id`, `surveillance` → `id`, `serology` → `id`, `strain` → `id`, `protein_feature` → `id`, `protein_structure` → `pdb_id`, `experiment` → `exp_id`, `bioset` → `bioset_id`, `genome_sequence` → `sequence_id`, `sequence_feature` → `id`, `ppi` → `id`. `dataResources` in `src/lib/data-api/types.ts` is the authoritative list and the `ids` map in `src/lib/data-api/resources.ts` the authoritative pairing; the pairs above are written out rather than given as two positional lists, because the older two-list form silently mis-paired every entry after the second once a resource was added in the middle. Check a resource against those two declarations, not against this line.
- Taxonomy IDs remain positive integer strings at route and selection boundaries. `genome_feature` also accepts `patric_id`; Surveillance and Serology allow their documented compound public identifiers. Identifiers remain strings even when digit-only.
- Resource metadata allowlists field type, selection, sorting, faceting, and RQL quoting. Requests are bounded and validated by resource, operation, identifier, field, operator, range/export size, URL/body size, and rate limit. Sorts gain the stable ID as a deterministic tie-break.
- Upstream item ranges use an exclusive end: `items=0-200` yields 200 rows. Collection pages are one-based and fixed at 200 rows.
- Anonymous public member lookups use five-minute shared caching (`s-maxage=300`); every other case is `private, no-store`. "Every other case" is authenticated requests, collections, selected-row requests, exports, **and any request at all while `E2E_MOCK_ENABLED=1`** — an E2E response is per-run fixture data and must never be shared across runs. `Vary: Cookie` is sent on both branches, because a response that is private today becomes shareable the moment the caller signs out. The gateway derives both the header and the upstream `cache`/`next.revalidate` init from one `sharedCache` flag returned by `resolveServerDataRepository`, so the route's answer to the client and its request to the upstream cannot disagree.
- `src/lib/data-api/route-errors.ts` owns the one `{error, code}` mapping both Data API routes answer with, so the gateway and the Taxa Tree route cannot drift on status or code for the same failure. `dataApiNotConfiguredMessage` is shared for the same reason. The *block* that detects the missing base URL, logs, and throws is shared too, but it lives in `server-policy.ts` rather than here, because it also needs the session lookup it must run before; `route-errors.ts` stays a pure response mapper. The operator-facing `console.error` wording is still per-route, because only the route knows which entry point is unconfigured — it is passed in as `notConfigured.log`.
- Rate limiting (`src/lib/rate-limit.ts`) is a process-local fixed-window counter shared by three routes: `/api/data/[resource]` and `/api/taxonomy-tree/[operation]` at 120 requests per minute per `clientIp` per resource/operation, and `/api/contact` at 5 per hour. Both Data API routes key the bucket *after* the allowlist check, so a garbage path segment cannot mint one. The bucket map is swept for expired entries only when it holds at least `pruneThreshold` (1,000) entries **and** at least `pruneIntervalMs` (60,000 ms) has passed since the last sweep — a size-only gate made a large *fresh* map re-scan on every request forever, evicting nothing. The interval is sized to the shortest caller window because a bucket only becomes prunable once its own window has ended: while the map stays at or above `pruneThreshold` and requests keep arriving, the retention bound is "its own window plus at most one interval" regardless of window length. Both conditions matter and neither is a defect — below the threshold no sweep runs at all (the map is capped at `pruneThreshold - 1` entries, so there is nothing to reclaim), and the sweep is opportunistic rather than timer-driven, so an idle process holds what it was holding until the next request. The gate relaxes physical eviction only; logical expiry is still checked per call against each bucket's own `resetAt`. **Two things are deliberately deferred there, not overlooked:** cross-process (Redis/Upstash) storage is blocked on knowing the real worker/replica topology, since consolidating per-process budgets silently changes the limit every client sees; and trusted-proxy hop selection is blocked on knowing the real reverse-proxy depth, since guessing the hop count is worse than trusting the chain. Both are documented at the code. Do not change either before the topology is settled.

### Taxa Tree route contract (`/api/taxonomy-tree/[operation]`)

- The Taxa Tree does **not** go through `/api/data/taxonomy`. It has its own same-origin route with two operations, `children` and `child-counts`, because it asks for one node's children in a single upstream range far wider than the gateway's fixed 200-row page and reads its child counts out of a `facet_counts` *response header* — neither of which the generic collection operation can express (it is fixed at a 200-row page and reads only the body).
- `src/lib/data-api/taxonomy-tree.ts` holds the whole contract: `taxonChildrenPageSize` (50,000), the two verbatim legacy RQL clauses (`and(gt(genomes,1),eq(parent_id,ID))&sort(+taxon_name)` and the `in(parent_id,(…))&facet((field,parent_id),(mincount,1))&limit(1)` form), the `Content-Range` paging safeguard, and `parseTaxonFacetCounts`. Keeping it out of `validation.ts` is what keeps the 50,000 bound unreachable from generic collection (`pageSize`) and export (`maxExportRows`) requests, and vice versa.
- Both operations reuse `ServerDataRepository` through `rangedRows` / `rangedHeaders` — narrow ranged reads that expose the response headers and take an explicit `start`/`end` that go verbatim into `Range`/`X-Range` under the same exclusive-end convention as every other range in this module, so the caller owns its own page bound and the repository shares no row limit between them. The tree's own window is `items=start-(start+taxonChildrenPageSize-1)`, byte-identical to the browser fetch it replaces, which under that exclusive end yields up to 49,999 rows per request — still far above the largest real taxon level, and the paging loop closes the gap regardless because the next `start` is the number of rows actually collected. Their `clause` argument is appended verbatim and does **not** pass through `validateRql`; the route is what guarantees it is built from digits-only parent ids.
- Responses are normalized JSON: `{rows}` (schema-validated with `taxonomyRecordSchema`) and `{counts}` (parent id → child count, keyed by decimal string). A parent with no qualifying children is **absent** from `counts` — that is what suppresses its expand arrow, which is why every malformed-facet shape has to fail rather than degrade into the same result.
- `parseTaxonFacetCounts` rejects: a missing header, invalid JSON, a non-object parse, a missing `facet_fields`, a missing/non-array `facet_fields.parent_id`, an odd-length array, a non-integer or non-positive parent id, a non-integer or negative count, a parent id that was not requested, and a duplicate parent id. Each is a 502 `malformed_response` whose detail reaches the client; the browser repository (`taxonomy-tree-client.ts`) prefixes it with `taxonomy child counts: `, so the caller-visible text is unchanged from when this ran in the browser.
- Child counts are capped at `maxRqlInValues` (500) parents per request — the Data API's own `in(...)` ceiling, not a limit of this route's own invention.
- Both answers vary with the caller's token, so both use `Cache-Control: private, no-store` with `Vary: Cookie`.

## Views & organism landing

`src/lib/views/`, `src/components/views/`, `src/hooks/views/`, `src/components/organisms/`, `src/app/(views)`, `src/app/organisms/`

- `src/lib/views/view-registry.ts` — enumerable, data-only route metadata for canonical segments, legacy redirects, search mapping, identifiers, resources, and defaults. Do not put components, fetch functions, columns, or tab query builders in it.
- `src/lib/views/collection-state.ts` — canonical URL-owned collection state. Pages are one-based, sort uses `field:asc|desc`, page 1/default sort are omitted, and filtering changes reset page 1. Page size (200), row selection, and column layout remain outside the URL. `collectionManagedParamNames`/`unionCollectionManagedParamNames` are the one definition of which query params a view (or several views at once) owns and may clear; filter→RQL composition is not here at all — `structural-rql.ts` is the only composer, and the options type carries no field map; `replaceCollectionSearchParams` (full-state replacement, no pagination reset — `useCollectionUrlState`'s `setState` just delegates to it) stays a separate function from `updateCollectionSearchParams` (incremental, resets page on a query-shape change) so the two policies can't get folded together again. Which of the two is live matters: `setState` is the only path the app takes, so the "filtering changes reset page 1" rule above is enforced by the caller passing an explicit `page: 1` (`resource-collection.tsx`'s filter-bar `onChange`), not by this module. `updateCollectionSearchParams` has no application caller today; it is retained, with its own tests, so the incremental policy does not have to be rediscovered by the first caller that needs it. `LandingShellClient` (`src/components/organisms/landing-shell/`) unions every organism-tab view's options via `unionCollectionManagedParamNames` to clear cross-tab state on a tab switch, since it can't otherwise know which tab a stray parameter belongs to.
- `src/lib/views/structural-rql.ts` — `structuralFilterRql(resource, state, options?)` is the one shared composer behind every `*StructuralRql` domain wrapper (Genome, Strain, Protein Feature, Epitope, Surveillance, Serology, Experiment/Bioset, Taxonomy, Protein Structure): explicit `state.rql` bypasses friendly filters, values within a field are ORed, fields are ANDed, and it serializes through the Data API `eq`. `options.fieldMap` remaps a friendly filter name to its backend field, and the one remap five of those wrappers need — `taxon_id` → `taxon_lineage_ids` — is the module's own exported `taxonLineageFieldMap`, passed as `fieldMap` by Epitope, Experiment, Protein Structure and Strain and spread into Genome's table (Taxonomy deliberately does not: `taxon_id` already is its own id field, which is why the map is opt-in rather than `fieldMap`'s default); `options.unknownFilters` picks what happens to a name absent from that map — `"passthrough"` (default, used by every wrapper above except Genome) forwards it unchanged, `"drop"` (Genome only) omits it instead, because Genome's remap table is total and authoritative rather than a set of overrides on top of pass-through. Each domain module still owns its typed wrapper function; the helper owns composition and the shared lineage remap. Genome's remap table is the one that is not just the shared map: it is *total* (`unknownFilters: "drop"`), so it is derived from `genomeCollectionOptions.friendlyFilters` rather than restating those names, and the two lists cannot drift apart. Feature (`src/lib/feature-view/query.ts`) is deliberately excluded: its synthetic protein filter accumulates outside the `state.rql` guard, so it applies even when explicit RQL is present, unlike every module above.
- `src/lib/views/field-metadata.ts` — `deriveFieldMetadata(fieldMap, policy)` is the one pass that turns a `src/constants/datafields/*` `DataField` map into a view's `{ columns, detailFields, facets, facetFields, sorts }`. Each entity calls it exactly once, from a `src/lib/*-view/fields.ts` module that both its `profile.ts` (columns/details/facets) and its `query.ts` (sort allowlist/friendly filters) import. A dedicated module for cohesion — the one metadata pass has one obvious home and neither consumer owns it. The alternative worth naming is the *unsafe* one: putting the pass in `profile.ts` and importing it from `query.ts` closes a cycle, because `profile.ts` already imports `query.ts` for `*StructuralRql`, and `query.ts`'s consumer is a module-level `const` (`export const featureSorts = featureMetadata.sorts`) while `*StructuralRql` is a hoisted declaration — so evaluating `profile.ts` first leaves `featureMetadata` in TDZ and throws. Putting the pass in `query.ts` instead would be safe (no `query.ts` imports `profile.ts`, so that direction closes no loop); `fields.ts` is preferred over it on cohesion, not safety. `child-resources.ts` runs the same pass for the three child-tab column sets whose resources have no `*-view/` directory (`genome_sequence`, `ppi`, `sequence_feature`) and consumes `columns` only, since child tabs hold their sort in component state rather than the URL. `genome_feature` is deliberately absent: `ResourceChildCollection` substitutes the Feature collection profile for its feature tabs, so a set declared there would be dead code, and it would also disagree on policy with that profile's columns even if declared — Feature passes `hiddenColumns: "omit"` while `child-resources.ts`'s derivations all use the default collapse policy.
  - **The one contract for the four overlapping visibility flags**, stated in the metadata's own terms, which used to be re-decided per entity:
    - **`show_in_table`** decides whether a field becomes a column *at all*. `false` ⇒ no column, and therefore no accepted sort. It is the only *flag-driven* gate on either; two explicit policy gates layer on top of it — `excludeFields` removes a field from every output including the detail projection, and `hiddenColumns: "omit"` removes the column (but not the sort) for `hidden` fields.
    - **`hidden`** decides a column's *initial visibility* (`visible: false`, revealable from the column-visibility menu) and **does not affect sortability**. It is a visibility flag, not a permission.
    - **`facet`** decides facet presence, and separately produces `facetFields` — the list entities spread into `friendlyFilters`. **`facet_hidden`** decides a facet's initial visibility (`initiallyVisible: false`). `facet_hidden` on a field that is not a `facet` is inert. Because `facetFields` comes from the `facet` flag alone, a *collapsed* facet is still a legal URL filter, and `facets` and `facetFields` are equal for all eleven resources that collapse. **They differ only for Feature, which is also the only resource that never reads `facetFields`** — it hard-codes `friendlyFilters: ["genome_id", "annotation", "feature_type", "filter"]` in `feature-view/query.ts`. So Feature's six omitted facets (`gene`, `product`, `plfam_id`, `pgfam_id`, `go`, `property`) are **not** legal Feature URL filters. Wiring `featureMetadata.facetFields` into that list would activate six filter names the view has never accepted — a behaviour change, not a tidy-up.
    - **Fields the registry declares array-valued are never sortable**, derived from the Data API registry rather than a hand-maintained per-entity set. `resourceRegistry[resource].fields[name].sortable` (`src/lib/data-api/resources.ts`) is already `!isArrayValued(name) && metadata.sortable !== false`, and it is the same value `validateSort` enforces at the gateway (`src/lib/data-api/validation.ts`), so `DataField.sortable` has exactly one consumer — the registry — and declared cardinality lives in the registry's `multipleFields` table. Strain's per-entity multi-value set was a verbatim copy of that table and is gone. Declared cardinality is what stopped Epitope's `host_name` and Surveillance's `pathogen_test_type` from advertising sortable headers whose sort the gateway rejects.
  - **Residual path — `multipleFields` coverage is incomplete.** It declares cardinality for 8 of the 16 resources. The eight resources without an entry are `genome`, `genome_feature`, `protein_feature`, `bioset`, `epitope_assay`, `genome_sequence`, `ppi`, and `sequence_feature`. Of those, `genome_sequence`, `ppi`, and `sequence_feature` are owned by `child-resources.ts`; `genome_feature` also appears in child tabs, but those tabs reuse the Feature collection profile instead. So a multi-valued field outside the declared eight is caught only if its metadata also says `sortable: false` — which is how `genome_feature.go` is handled (declared `cardinality: "scalar"`, `sortable: false`). Both routes land in the same registry `sortable` answer, so nothing is currently wrong, but the registry is not yet the single source of cardinality truth it is for the eight. Widening `multipleFields` is future work; until then read "array-valued" in this contract as "declared array-valued".
  - **Two per-resource differences remain, and are deliberate rather than accidental — documenting them is the point of this contract, not resolving them by deleting behaviour:**
    - **Feature excludes `facet_hidden` fields from its facets entirely** (`hiddenFacets: "omit"`), because its six high-cardinality hidden facets — `gene`, `product`, `plfam_id`, `pgfam_id`, `go`, `property` — time the upstream combined facet query out. **Strain and every other resource include them, collapsed.** Same flag, different policy, for a real upstream reason. The per-resource facet-composition guard in `collection-field-contract.test.ts` pins the other eleven to "collapse, never omit", so adding `hiddenFacets: "omit"` elsewhere fails loudly rather than silently dropping facets (it would drop 24 for Genome and 17 for Surveillance).
    - **Feature omits a `hidden` field's column entirely** (`hiddenColumns: "omit"`); **Strain and every other resource merely collapse it**, leaving it toggleable. That residual disagreement over what `hidden` means for a column is now written down instead of being re-invented per module.
  - Because `hidden` does not affect sortability (see the `hiddenColumns` gate above), **Feature is the one resource whose sort allowlist is wider than its sortable columns**: its 23 hidden scalar fields keep working sorts (`sort=plfam_id:asc` orders rows correctly) while rendering no column. The invariant therefore runs in one direction only — *every sortable column is in the allowlist*, so the table never offers a header the URL refuses — and `collection-field-contract.test.ts` asserts that a sort with no column behind it can only ever be a `hidden` field.

## Detail panel metadata links (search results)

`src/components/detail-panel/info-panel.tsx` (the search variant, `renderSearchInfoPanel`) renders per-tab metadata fields from `src/constants/datafields/*` for the search results detail panel — a separate rendering path from the `*-view` collection/member pages above, and from their table columns.

The link boundary itself is **not** in that file. It lives in two siblings, so the link-rendering entity overviews under `src/app/(views)/` share it rather than each re-deriving a scheme check: `src/components/detail-panel/metadata-link-policy.ts` (pure — `classifyHref`, `resolveLink`, `isLinkValue`) and `src/components/detail-panel/metadata-link.tsx` (rendering — `MetadataLink`, `renderMetadataLink`, `renderMetadataLinkButton`, `metadataLinkClassName`).

- **One classification rule for every link shape.** `classifyHref(href)` (in `metadata-link-policy.ts`) returns `"internal"` (an unambiguous same-origin path — `startsWith("/")` and explicitly not a protocol-relative `//host`), `"external"` (an absolute `http(s)` URL, opened in a new `noopener`-isolated tab), or `"unsafe"` (anything else — a bare `//host`, a `javascript:`/`mailto:`/other non-http(s) scheme, or a string that is neither). `"unsafe"` renders nothing at all — no anchor, no `Link` — rather than guess. Scalar, array, and `linkType: "button"` fields all go through the same `renderMetadataLink`/`renderMetadataLinkButton` helpers, and the four link-rendering entity overviews (`genome`, `feature`, `epitope`, `experiment`) through the `MetadataLink` component that `renderMetadataLink` itself wraps, so a link's *shape* never changes its routing or security contract. Its **call site still can**, and one does: `src/components/shared/data-table.tsx` renders the same `DataField.link` templates through its own `valueHref` path with no `classifyHref` call, no `target` and no `rel`, fed by the three profiles that forward `link` to `valueHref` (see the `adaptColumn` bullet above). Several of those templates are absolute external URLs, so the same InterPro or NCBI link opens in an isolated new tab from the detail panel and navigates in the same tab from the collection table. Bringing `valueHref` onto the boundary is a collection-table behaviour change and is deliberately not done here. There used to be a fourth, inconsistent path here: scalar links were rebased onto a hardcoded `https://www.dxkb.org` origin and always rendered as external new-tab anchors, so a canonical relative link like `/genome/{value}` left the current deployment (staging, a preview, localhost) instead of navigating internally; and the original two-way `isExternalHref` check treated "not external" as "therefore internal", which would have handed a protocol-relative `//host` or a `javascript:` URI straight to `Link` with no `target`/`rel` isolation (latent only — no current template can produce one, since `resolveLink` always `encodeURIComponent`s row-supplied segments — but the boundary needed to hold regardless of today's data). Plan item 20B removed the origin rebase and unified all three shapes onto `classifyHref`; a same-day review added the third `"unsafe"` outcome.
- **`detail-key-value.tsx`'s `DetailField` carries no `href`.** Every link-bearing field is built as `render: () => ReactNode` in `info-panel.tsx`, which routes every destination through the `metadata-link` boundary rather than classifying inline; `DetailKeyValueTable` stays a pure presentational renderer (plain value, date formatting, or a supplied `render()`) with no knowledge of internal-versus-external destinations. `DetailKeyValueTable` has exactly one consumer (`info-panel.tsx`, via `DetailPanel.KeyValueTable`), so this is a safe, complete contract change rather than a partial one.
- **`resolveLink(template, row, fallbackField)`** (also in `metadata-link-policy.ts`) fills `{placeholder}` tokens against the row. `{value}` is a sentinel that never matches a real row key, so it always falls back to the field's own value; a real field name like `{genome_id}` matches the row directly (row-aware — e.g. `genome_feature.genome_name`'s link points at `/genome/{genome_id}`, not its own value). It returns `undefined` — rejecting the link outright, so the field falls back to plain-text rendering — when any placeholder has no resolvable primitive value, rather than emitting a URL with a missing or literal `{...}` segment.
- **Ruling: `enableRowLinks` and metadata links are independent, by design.** `enableRowLinks` is an optional `ResourceCollection` prop, defaulting to `true`, and each per-resource `*-resource-collection.tsx` wrapper that exposes it simply passes it through; it governs only whether a collection table row click navigates to the entity's member page, by gating the row-link column mapping in `resource-collection.tsx`. It has no interaction with `DataField.link` or this detail panel: the Taxa Tree tabs that set `enableRowLinks={false}` (`src/components/organisms/taxon-views/*.tsx`) do so as a deliberate legacy-parity call about row navigation, and it neither activates nor suppresses a metadata link. This was previously an implicit, undocumented divergence; it is a decision now, not an oversight.
- **Datafields audit (item 20B).** Swept `src/constants/datafields/*` for legacy `/view/*` routes, hardcoded production origins, and plain-http targets. Fixed: `strain.taxon_id`, `genome_feature.taxon_id`, and `epitope.taxon_id` converged from the stale `/view/Taxonomy/{value}` onto `/taxonomy/{value}` (matching Protein Feature's already-canonical destination); `genome.contigs` moved from a hardcoded `https://www.dxkb.org/view/Genome/{genome_id}?activeTab=sequences` to the row-aware internal `/genome/{genome_id}?tab=sequences` (the genome-view `sequences` tab — the old `activeTab` param was never read by the new page anyway, since `src/proxy.ts`'s internal-redirect step only rewrites `?view=` to `?tab=`, not `?activeTab=`); `protein_feature.refseq_locus_tag` moved from plain `http://` to `https://`. `genome_sequence.sequence_id`'s legacy `/view/FeatureList/?and(eq(annotation,PATRIC),eq(sequence_id,{value}),eq(feature_type,CDS))` was rewritten onto `/feature?rql=and(eq(annotation,PATRIC),eq(sequence_id,{value}),eq(feature_type,CDS))` — not a guess: `src/proxy.ts`'s live `/view/*` redirect (`mapLegacyViewPath`, matcher includes `/view/:path*`) maps that exact legacy path+query to this exact `/feature?rql=...` form (`FeatureList` → segment `feature`, a query string with no top-level `name=` pair is forwarded verbatim as `rql=`), and `validateRql("genome_feature", "and(eq(annotation,PATRIC),eq(sequence_id,X),eq(feature_type,CDS))")` round-trips unchanged through the real RQL validator — the same `annotation`/`feature_type` pairing `feature-view/query.ts`'s `proteinFeatureRql` already uses for "Proteins" filtering. This item's scope is the detail panel only, per plan item 15's boundary — no `DataTableColumn.valueHref` (table-column link destination) was activated, and both of item 15's named carve-outs (Strain's NCBI accession fallback, Protein Feature's `patric_id` fallback) are untouched. But two of the fixes above land on fields Strain's and Protein Feature's `adaptColumn`s (`strain-view/fields.ts`, `protein-feature-view/fields.ts`) already forward verbatim to `valueHref` — `strain.taxon_id` and `protein_feature.refseq_locus_tag` are each a single shared `DataField` object read by both the detail panel and that resource's table column. Correcting the stale route/scheme at that one shared source therefore corrects both surfaces' `valueHref` too, as a deliberate and necessary consequence of fixing the datafield, not a new activation — `collection-field-contract.test.ts`'s Strain adapter test was updated accordingly.

## Services pattern

- Each bioinformatics service is a form page under `/services/`
- Forms use TanStack Form (`@tanstack/react-form`) + zod validation
- Submission: `useServiceFormSubmission` hook → `submitServiceJob()` → `AppService.start_app2`
- `ServiceDebuggingProvider` wraps service layouts; enables a debug mode that shows params instead of submitting
- Form parts come from the wrappers in `src/components/services/form-ui/` (`ServiceCardHeader`/`Title`/`Content`, `ServiceLabel`, `ServiceSubLabel`, `ServiceFieldLabel`, `ServiceFieldSubLabel`, `ServiceFieldItem`, `ServiceSelectTrigger`/`Content`, `ServiceInput`, `ServiceNumberInput`, `ServiceTextarea`, `ServiceRadioGroup`, `ServiceCollapsible`/`Trigger`/`Content`, `ServiceRequiredLabel`). Each applies one global `service-*` class from `src/app/globals.css` to the `ui/` part it wraps; do not put those classes on `ui/` components directly. `RequiredFormCardTitle` (`src/components/forms/required-form-components.tsx`) renders `ServiceCardTitle`, so it needs no class. `CardFieldLabel`/`CardFieldInput` carry the legacy `card-sublabel`/`card-input` classes the home page search uses, which differ from the `service-*` ones.

## Rerun pre-fill pattern

- `useRerunForm<T>()` reads job params from `sessionStorage` (keyed by `?rerun_key=`) and returns `{ rerunData }`
- Pre-fill is auto-applied via the hook's declarative options (`fields`, `libraries`, `syncLibraries`, `onApply`); the hook self-manages one-shot application internally
- The sessionStorage entry is intentionally NOT consumed on read because React rendering may remount the form; consume-on-read could null out a subsequent mount
- Library reconstruction helpers in `src/lib/rerun-utility.ts`:
  - `buildPairedLibraries(rerunData, getExtra?)` — paired-end libs from `paired_end_libs`
  - `buildSingleLibraries(rerunData, getExtra?)` — single-end libs from `single_end_libs`
  - `buildSraLibraries(rerunData)` — SRA libs from `srr_libs` with `srr_ids` fallback
  - Pass a `getExtra` callback to merge service-specific fields (e.g. `platform`, `interleaved`)

## Data fetching

- TanStack Query for all async state (client-side)
- View collections and member detail panels use `src/hooks/views/` over the `DataRepository` boundary in `src/lib/data-api/`; components do not parse upstream wire formats.
- Custom hooks in `src/hooks/services/workspace/` wrap workspace API calls
- `src/lib/api/client.ts` uses credentialed fetch; only the app-specific `session_expired` code triggers one hard reload, while ordinary upstream 401 responses remain API errors

## UI

- shadcn/ui (New York style, slate base) in `src/components/ui/`, built on `@base-ui` primitives (e.g. https://ui.shadcn.com/docs/components/base/accordion)
- Tailwind CSS v4 with CSS variable theming; multiple named themes in `src/app/globals.css`
- SVG via `@svgr/webpack` (`import Icon from './file.svg'` or `'./file.svg?url'` for raw URL)
- `sonner` for toasts; `lucide-react` for icons
